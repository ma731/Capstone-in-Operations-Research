Your test suite, explained

202 automated tests, six jobs. What each one checks, in plain words, so you can defend them.

First: why so many tests on a "we found nothing" result?

Because the weak spot of a null result is the accusation "you didn't look hard enough, or you moved the goalposts." The test suite is the answer to that. It proves the machinery is correct, the thesis's own math holds, and not one reported number can quietly change.

The one-liner for the viva: "The tests are what make a negative result credible instead of just asserted. A wrong model reproduces byte-for-byte too, so reproducibility is hygiene; the tests go further and enforce the actual claims."

Why 202 locally but 189 in CI? The 13 test_electricitymaps tests read the raw Electricity Maps carbon data, which is under a non-redistribution licence and is never committed. On the public CI runner that data is absent, so those tests skip (they are marked pytest.mark.skipif, not failed). With the data present locally, all 202 run.

The six jobs the tests do

70Every scheduler vs a known-correct answer
test_algorithm_1, test_algorithm_2a, test_algorithm_2b_mahalanobis, test_transfer_dro, test_online_transfer, test_phase2_copula

Checks Each solver is run on a small, hand-built problem where the right answer is known, and it must match it. Also: constraints are respected, bad input is rejected, and each model reduces to what the maths says it should.

Why If the optimiser is wrong, nothing downstream means anything. This is the foundation.

Example test_robust_value_is_mean_plus_penalty: confirms the robust plan really equals mean + ε·||Lᵀx||, i.e. it collapses to a mean term plus a cone penalty, exactly as the thesis claims.
Example test_transfer_reduces_emissions: with a clean region available, turning transfer on must strictly cut emissions vs transfer off. test_transfer_conserves_work: flows move work, never create or destroy it.
59The covariance and dependence tools
test_covariance, test_stratified_correlations, test_tail_dependence

Checks The maths tools that measure how regions move together: turning a schedule into a vector and back (round-trips), the "shuffle" that destroys cross-region links, correlations, and the tail-dependence coefficients.

Why RQ2 lives or dies on these being correct. If the shuffle or the tail measure were buggy, the null would be meaningless.

Example test_comonotone_has_full_upper_tail_dependence and test_independence_has_low_tail_dependence: the χ estimator returns 1 for perfectly-linked data and ~0 for unrelated data, so the 0.48-vs-0.25 numbers on slide 20 are trustworthy.
25The shared rulebook (the fair-test constraints)
test_constraints_taskA, test_capacity, test_carbon_budget

Checks The constraints every scheduler must obey: capacity, ramp limits, the variable-capacity field, and the carbon budget. E.g. a budget below the minimum is correctly flagged infeasible; a slack budget matches the unconstrained solution.

Why The whole method is "only the brain changes." These tests enforce that every version runs under identical rules, so any difference is the model, not the setup.

16The data pipelines
test_electricitymaps (13, data-gated), test_temperature (3)

Checks Loading the real data correctly: files parse, a leap year has 8784 hours, timestamps are UTC, carbon intensity is non-negative. Temperature (Open-Meteo, CC-BY) is committed, so its 3 tests always run.

Why Garbage in, garbage out. These 13 are the ones that skip in CI because the licensed carbon data is not public.

11The thesis's own maths, run as code  ⭐
test_claim_binding, test_part5_condition

Checks This is the unusual one. Each test pins a statement the thesis makes, so the central arguments are enforced on every code change, not just proved on paper.

Why This is your strongest "trust me" evidence. If a load-bearing claim ever broke, the build would go red. See the spotlight below.

21Frozen numbers: nothing can drift  ⭐
test_carbon_ceiling_snapshot, test_risk_measure_swap_snapshot, the headline guard in test_transfer_dro, test_emergency_inject, test_es_pt_fr, test_baseline_components_v11, test_plots

Checks Every headline number is re-checked against its archived CSV, so a code change cannot silently change a number the thesis reports.

Why It closes the "did you move the goalposts?" attack: the goalposts are pinned in version control. See the spotlight below.

Spotlight 1: the thesis's maths, enforced in code

These four are the ones to name if an examiner asks "what makes this rigorous?" Each is a theorem from the thesis, checked on every push.

CVaR translation-invariance

test_translation_invariance checks CVaR(e + c) == CVaR(e) + c for random shifts. This is the algebraic backbone of the whole mechanism: the shared daily mean field passes straight through the risk score, so it cannot interact with the dependence model. That is why the co-movement layer can only touch the small leftover.

Proposition 1's bound, on a real solve

test_solved_optimal_value_gap_within_bound actually solves the DRO on a toy instance and checks |OPT(Σ) − OPT(Σ_shuffled)| ≤ ε·max||x||·√||Σ_off||. The gap between the real-links and links-destroyed schedules is provably bounded by the size of the cross-region block. Not just claimed, run.

Mean-dominance, as a property

test_growing_mean_field_shrinks_relative_spatial_gap scales the daily mean up (1x, 2x, 4x, 8x, 16x) and checks the relative spatial gap shrinks every time, ending below 5% of where it started. This is the wave-and-ripple mechanism, demonstrated: a bigger wave drowns the fixed ripple.

The shuffle is legitimate

test_shuffle_preserves_psd checks that destroying the cross-region links still leaves a valid covariance matrix. So the falsification test compares two legitimate models, not one real model against a broken one.

Spotlight 2: the numbers are pinned

The snapshot guards re-verify the reported headlines against saved files. Two worth naming:

The RQ3 crossover claim is literally asserted

test_carbon_ceiling_matches_thesis pins the joint severities (1.34, 1.29, 1.89) and then asserts joint_max < 3.0 — the code itself enforces that no real grid reaches the M≈3 crossover. It also pins BPAT 5.1x and Uri 1.3x.

The RQ1 headline is pinned and internally consistent

test_transfer_value_headline_matches_snapshot pins 4.0 / 9.9 / 9.0% and re-derives them from the raw CVaR columns ((c0 − cT)/c0), so the number cannot be right by luck or stale.

The robustness "generality" probe is guarded too

test_meanvar_swap_does_not_rescue_covariance pins that swapping to a covariance-amplifying objective still does not make covariance pay (it hurts by 0.84% and 1.50% on two grids), while test_swap_moves_the_schedule confirms the schedule moved >20% — so the small gap is not because the objective ignored covariance.

If they ask about the tests, say this

"Tell me about your test suite."

202 automated tests in six groups: 70 check every scheduler against known-correct answers, 59 check the covariance and tail-dependence tools, 25 enforce the shared feasible set, 16 check the data loaders, 11 pin the thesis's own theorems as executable tests, and 21 freeze every reported number against an archived file. They run in CI on every push; 189 run on the public runner because 13 need the licensed carbon data.

"Isn't reproducibility just hygiene?"

Yes, and I say so. A wrong model reproduces byte-for-byte too. That is exactly why the claim-binding tests go further: they enforce the load-bearing maths, like CVaR translation-invariance and the Proposition 1 bound, so a broken claim turns the build red. That is what makes the null auditable rather than asserted.

"How do I know the null isn't a bug in the shuffle?"

Two ways. test_shuffle_preserves_psd proves the shuffled matrix is still a valid covariance, so both arms are legitimate. And the positive control fires at +1.46% on the same code, so the pipeline can detect a real effect when one exists.

"What could a test have caught that you didn't expect?"

The mean-dominance monotonicity test is a genuine property check, not a fixed number: if the mechanism were wrong, scaling the mean up would not shrink the gap, and the test would fail. It encodes the mechanism, so it would catch a mistake in my own reasoning, not just in the code.
